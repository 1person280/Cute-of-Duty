# CLA 签署台账（CLA Signatures）

> 用途：记录每一个向本项目提交过贡献的身份是否已同意 [CLA](../CLA.md)，
> 作为项目方对贡献代码行使著作权（含再许可与追责）的凭据。
> **任何人合入首个 PR 前，必须先在本台账登记签署。**

## 签署方式

- 在 PR 描述（或首次贡献的 Issue）中写入**原文声明**：

  ```
  I have read the CLA Document and I hereby sign the CLA.
  ```

- 由维护者在本台账登记（或后续接入 CLA 机器人自动追加）。
- 实体 / 雇主代理提交时，另需说明所代表实体名称与授权身份。

### 结论（已定案）

- 身份 #2 `Bzhan-3493264141322312` **不是第三方贡献者**，而是 AI 编程工具（ZCode）
  在提交 `d857e61`「萌系召唤首个真开源版本」（2026-09-10）时**误填的 author 元数据**。
  该提交的实际创作者为项目方本人。
- **法律判定**：著作权归属取决于**实际创作者**，不取决于 git 的 `author` 字段；
  元数据错误**不产生任何第三方权利**，许可链**无缺口**，**无需**任何第三方签署 CLA。
- **处置**：根目录新增 [`.mailmap`](../.mailmap) 将该误填身份映射回 `1person280`，
  在 `git log` / `git shortlog -sne` / `git blame` / GitHub 署名中统一校正归属。
  该方式**不重写历史、无需 force-push、不影响任何已 clone/fork 的仓库**。
- 因此本项目**不存在需要追溯补签的第三方**；身份 #1 若为项目方本人，追溯补签即为
  **形式闭合**（开一个 `[CLA] 历史贡献追溯签署` Issue，本人回复一次声明即可）。

### 追溯签署操作步骤

1. 项目方在本仓库开一个 Issue，标题：`[CLA] 历史贡献追溯签署`。
2. 请各历史贡献者在该 Issue 下**原样回复**：

   ```
   I have read the CLA Document and I hereby sign the CLA.
   ```

3. 维护者在本台账对应行补上「CLA 版本 / 签署日期 / 方式」，并登记被覆盖的提交范围
   （可执行 `git log --author=<身份> --format=%h` 取得）。
4. **联系不上或拒绝签署的第三方贡献** → 按 [CONTRIBUTING.md](../CONTRIBUTING.md)
   处理：对该部分代码做 **clean-room 重写**并用重写版本替换，彻底消除许可缺口，
   **不得**在原贡献之上继续叠加。
