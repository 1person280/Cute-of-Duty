# 改动前拷问（plan-interrogation）

## 零、这个技能解决什么

AI 最贵的失败不是 bug，是**做完才发现解的是另一个问题**。

根因很朴素：你说两三句话，AI 热情地替你把五个没定的决策都定了，然后照着错的假设写 250 行。

本技能把「动手前」这段对话强制成一次面试。方法论改造自 Matt Pocock 的 `grill-me`（MIT），**提问清单换成本项目的硬约束红线**——通用技能不会问你「这个文件会不会破 600 行」「要不要 `y+1`」，而这些在你项目里才是真正卡死的东西。

一句话判据：**没复述完整份计划并获你确认之前，一行代码都不写。**

---

## 一、四条铁规（来自 grill-me，原样保留）

1. **把计划当成决策树，不是文档。** 先找「其他决定都挂在它上面」的根决策；父决策定了再问子决策——上游答案会改变下游什么值得问。
2. **一次只问一个问题。** 问完停下，等回答。Q2 的答案常常取决于 Q1，一次性抛出一串问题会把你按在组合空间里。
3. **每问必须附自己的推荐答案 + 一句理由。** 你只做判断题：确认 / 推翻 / 改方向。**只提问不给推荐答案视为违规**（纯苏格拉底式空问会把人问死）。
4. **能自己查的不许问你。** 见第四节。事实是 AI 的活，判断题才是你的活。

---

## 二、先静默分级（不问用户，先自己查）

不搞一视同仁的六十连问——那会把小改动拖成负担。先读代码与文档判定等级，再决定拷问深度：

| 等级 | 判据 | 拷问深度 |
|---|---|---|
| **L0 局部** | 单文件内改动，不碰对外接口 / 线格式 / 配置语义 | 2–4 问，只问边界与验证 |
| **L1 模块内** | 跨文件、改模块内部结构，不改对外接口 | 4–8 问 |
| **L2+ 契约** | 碰模块边界 / 公共 Trait / 线格式 / 配置语义 | 第三节全清单逐条过 |

分级依据自己查：`docs/architecture/module-boundaries.md`、`docs/adr/`、`docs/contracts/*.yaml`、`git log`。

## 三、项目专属提问清单

L2+ 全过；L1 只挑相关条目；L0 只留 3.5 与 3.6。**每一条如果答案在代码里，先去查再决定要不要问。**

### 3.1 洁癖

- 改动涉及的文件会不会破 **600 行**？破了拆成哪个语义单文件、还是哪个子域目录？
- 新增文件名有没有**下划线**？要不要开子域目录？（开了，嵌套是否真有意义？）
- 有没有引入 `utils.rs` / `common.rs` / `misc.rs` / `helpers.rs` 这类通用名？
- 新增公开项有没有写好 **Why 型 Rustdoc**（解释设计理由，不是复述代码）？

### 3.2 架构

- 有没有**跨模块直接调用**（`use crate::<别的模块>::`）？若有，改走哪条 trait / 事件？
- 这份数据**所有权归谁**？下游只持快照还是句柄？
- 依赖方向对不对：表现层 → 契约层 → 领域层 → 基础设施层？
- 会不会形成**环**？
- 跨 crate / 跨进程要不要先落一个 `XxxPort` trait？
- HostCode / ServerCode 归属划线对不对（「应该算什么」必须服务端权威）？

### 3.3 协议

- 碰不碰 L2+ / 线格式 / 配置语义 / 公共 Trait？
- 碰了 → 是**兼容变更（`z`）**还是**不兼容变更（`y+1`）**？不兼容必须附**迁移指南**。
- 契约 YAML（`protocol.yaml` / `web.yaml`）要不要同步改？
- **BarekHistory** 这次写什么、写进哪个版本节？

### 3.4 文档

- 碰到的模块要不要同 PR 补该模块的 `module.md`？（现状 0，「碰到就补」）
- 破坏性 L1 变更要不要写 **ADR**？编号接哪个？
- README 的模块表 / 版本表要不要跟着改？

### 3.5 测试与验证

- 这次改动的验证命令是哪几条？
  `cargo-wrap check --workspace` / `cargo-wrap test -p cute_of_duty_server` / `cargo-wrap build --workspace --release`
- 服务端权威逻辑的**确定性**怎么验？
- 表现层改动怎么实机看？
- 编译一律走 `tools/cargo-wrap/target/release/cargo-wrap.exe`，**禁裸 `cargo`**——这条也让用户确认知道。

### 3.6 版本号

- 统一版本号 `x.y.z` 这次哪一段 `+1`、为什么？（`x` 游戏内核 · `y` 协议 · `z` 细节）
- 是否要标**预发布**？

## 四、什么时候不许问（先去查）

以下信息一律自己查，**不许拿它当问题消耗用户时间**：

| 要查的 | 去哪查 |
|---|---|
| 已有约定与写法 | 读相邻同类文件 |
| 模块边界与成熟度分级 | `docs/architecture/module-boundaries.md` |
| 历史决策 | `docs/adr/` |
| 线格式与字段 | `docs/contracts/*.yaml` |
| 版本与变更台账 | `docs/barek-history.md` + `Cargo.toml` |
| 编译与验证的正确姿势 | `CONTRIBUTING.md` + `tools/cargo-wrap/` |

查完仍不确定的，**把查到的事实带进问题**再问：
> 「README 写的是 X，代码里是 Y，以哪个为准？」

这才算有效提问。

---

## 五、收尾：复述 → 确认 → 才动手

决策树关完（每个未决项要么已定、要么你明确说「执行时再定」、要么明确出界）后，**停下来**，把整份计划复述给你：

1. 本次要做的事（一句话）
2. 已定的决策清单（逐条，含接受的取舍）
3. **明确不做什么**（逐条——最容易跳过，也最关键）
4. 改动面（哪些文件 / 模块 / 契约）
5. 验证命令
6. 版本号判断

等你确认后才开工。**确认前不动手**，包括「顺手先建个文件」这类小动作。

---

## 六、可选落盘（先问，不要自动写）

复述稿确认后，按需落盘：

- 大改动 → 迁移/改造计划文档（参照 Bevy 弃用 Bundle 迁移计划的结构：前置依据 → 全量清单分批次 → 改造范式 → 执行顺序 → 验证命令）
- 破坏了 L1 → 追加 ADR
- 碰了契约 → 追加 BarekHistory 条目

---

## 七、反模式（踩了即违规）

- 一次抛多个问题（「schema 是什么？API 呢？鉴权呢？」）
- 只提问，不给推荐答案
- 问一个自己能从仓库里查到的事实
- 没问完就动手，或边问边改
- 跳过「明确不做什么」
- 对 L0 小改动也上全套六十问
- 越界：3D 地图/关卡交给 `map-acceptance`，提交/推送/发布交给 `compliant-delivery`

---

## 八、与其他技能的边界

| 技能 | 管什么 | 什么时候切过去 |
|---|---|---|
| **plan-interrogation（本技能）** | 动手前的决策拷问 | 通用工程改动（功能 / 升级 / 协议 / 重构） |
| `map-acceptance` | 地图需求采访 + 白模→材质→光照→装饰→终验分层验收 | 议题是 3D 地图 / 场景 / 关卡 |
| `compliant-delivery` | 提交 → 推送 → 发布三闸门 + 五道红线 | 代码已改完，要落地 |
| `game-art-creation` | 程序化生成美术资产 | 议题是图标 / 贴图 / 建模 |

四者构成闭环：**拷问（事前）→ 美术/地图（域内）→ 交付（事后）**。
